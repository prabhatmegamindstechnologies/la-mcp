# Bug: Vercel build log shows TS2688 "Cannot find type definition file for 'node'"

- Date: 2026-11-20
- Flow: BUG_FIX
- Status: PLAN (waiting for the user's "yes")

## Symptom

The Vercel build log for la-mcp shows this error:

```
error TS2688: Cannot find type definition file for 'node'.
  Entry point of type library 'node' specified in compilerOptions
```

It doesn't stop anything: the build completes, the deployment works, `/health` returns `{"ok":true}`, and `scripts/oauth-check.ts` passes against https://la-mcp-three.vercel.app. Locally, `npm run typecheck` with TS 7.0.2 is clean.

## Root cause

- **Proven:** `@types/node` is installed on Vercel. The log says "added 111 packages", and 111 is exactly the number of packages in `package-lock.json` for Linux x64, development dependencies included.
- **Likely, not confirmed:** Vercel's builder ("Using the TypeScript 7.0.2 compiler executable") type-checks the function with its own setup. It reads `compilerOptions.types: ["node"]` and resolves that name from a different folder than the project, so it can't find the package. I'm inferring this from the log; Vercel's internals can't be checked from here.

## Fix

1. `tsconfig.json`: remove `"types": ["node"]`.
2. Load the Node types from inside the code instead, with `/// <reference types="node" />` at the top of:
   - `api/index.ts`, the entry Vercel builds
   - `server.ts`

   A reference inside a file is resolved from that file's own folder, so `node_modules/@types/node` is found the same way locally and on Vercel. TypeScript 6 and later include no `@types` packages by default, so the local check gets the types only through these references.
3. Verify locally:
   - `npm run typecheck` is clean
   - `npm test` passes 37/37
4. Commit and `git push`. Vercel deploys automatically.
5. Verify on Vercel:
   - the new build log has no TS2688
   - `/health` returns ok
   - `oauth-check.ts` passes against https://la-mcp-three.vercel.app

If TS2688 is still there after step 5, revert the change and accept the warning. It does no harm; the build was succeeding anyway.

## Rejected alternatives

- **Ignore it:** it does no harm, but a red error in every build log hides real errors later.
- **Downgrade to TypeScript 5:** the CMS uses TS 7, and a downgrade is a bigger change than this needs.
- **`typeRoots` in tsconfig:** it's also resolved relative to the config, so it would probably fail the same way.
